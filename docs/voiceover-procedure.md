# VoiceOver 検証手順 (macOS)

`ariaSnapshot` はアクセシビリティツリーの構造を機械的に比較できるが、
「スクリーンリーダーが実際にどう読み上げるか」までは保証しない。
そこを埋めるのがこの VoiceOver 検証。

**classic (localhost:4173) と vapor (localhost:4174) で完全に同じキー操作を行う**
ことが唯一かつ最重要のルール。操作が違えば読み上げの違いが Vapor 起因か
操作起因か切り分けられなくなる。

## 事前準備

### 1. ビルドとガード検証

**先に `pnpm run verify` を通す。** Vapor モードが効いていない状態で読み上げを
比較しても、それは classic 同士を聞き比べているだけになる。ariaSnapshot と違って
読み上げ検証は手作業なので、後から気付いても全カテゴリやり直しになる。

```sh
pnpm run sync && pnpm run typecheck && pnpm run build && pnpm run verify
```

`pnpm run build` はクライアント用のビルドに続けて SSR ビルドとプリレンダ
(`build:ssr` → `prerender`) まで走らせる。項目11 が開く `/ssr.html` は
ここで生成されるので、**このコマンドを省略すると項目11 だけ 404 になる**。

### 2. プレビューサーバの起動

別々のターミナルで起動し、検証中は両方立てたままにする。

```sh
pnpm run preview:classic   # → localhost:4173
pnpm run preview:vapor     # → localhost:4174
```

**ビルドは含まれていない。** 手順1で `verify` を通した成果物をそのまま配信するため。
ここで再ビルドすると、検証した成果物と配信する成果物が別物になりうる。

ポートは `scripts/lanes.mjs` の `previewPort` が単一の情報源で、`strictPort: true`
が付いている。埋まっていれば別ポートへ逃げずに失敗する。

```
error when starting preview server:
Error: Port 4173 is already in use
```

これは意図的な仕様。逃げてしまうと、例えば 4174 が埋まっていて vapor が 4175 で
起動し、4173 に残った classic を相手に「classic 同士」を比較する事故が起きる。
VoiceOver は何も言わずに読み上げるので、この事故は自力では気付けない。

### 3. どちらの lane を操作しているかの確認

タブのタイトルが `classic` / `vapor` になっている。カテゴリを移るたびに確認する
(`index.html` の `<title>` を lane ごとに変えているのはこのため)。

### 4. キャプションパネルの有効化

読み上げ内容を画面に字幕表示させると、録画にそのまま残るので後から検証できる。

1. VoiceOver を起動 (⌘ + F5)
2. VoiceOver ユーティリティを開く (VO + F8)
3. 「ビジュアル」→ 「キャプションパネル」を有効化

### 5. 録画の準備

- QuickTime の画面収録、またはショートカット ⇧⌘5
- **マイクを ON** にすると読み上げ音声も残る

## 実行手順 (項目ごとに classic → vapor の順で同一操作)

読み上げ全文は聞き取りではなくキャプションパネルの表示テキストを
そのまま書き写すこと (聞き取りだと表記ゆれが入る)。

**カテゴリを移動するたびにページを再読み込みする。** 前の項目の操作で
残った状態 (開いたダイアログ、表示済みのエラー) が次の読み上げに混ざると、
差分の原因を切り分けられなくなる。

### 1. live region: トースト通知

| # | 操作 | キー |
|---|---|---|
| 1 | ページを開く | Safari で対象 URL へ |
| 2 | フォーカスを「保存」へ移動 | `Tab` |
| 3 | 読み上げを記録 | (自動読み上げ) |
| 4 | ボタンを押下 | `VO + Space` |
| 5 | live region の読み上げを記録 | (自動読み上げ) |

`role=status` は控えめな通知であり、読み上げ中の内容を中断しない。
中断されるようなら差分として記録する。

### 2. フォーカス管理: モーダルダイアログ

| # | 操作 | キー |
|---|---|---|
| 1 | フォーカスを「設定を開く」へ移動 | `Tab` |
| 2 | 押下してダイアログを開く | `VO + Space` |
| 3 | 開いた直後の読み上げを記録 | (自動読み上げ) |
| 4 | フォーカスを「閉じる」へ移動 | `Tab` |
| 5 | 押下して閉じる | `VO + Space` |
| 6 | 閉じた直後の読み上げを記録 | (自動読み上げ) |

**この項目が最も差分の出る可能性が高い。** 見るべきは3点。

- ダイアログを開いたとき「ダイアログ 表示設定」のようにロールごと読み上げるか
- 閉じたときフォーカスが「設定を開く」に戻り、それが読み上げられるか
- ダイアログの外に `VO + →` で出られてしまわないか (`aria-modal` の効き)

### 3. 動的 aria 属性: 開閉パネル

| # | 操作 | キー |
|---|---|---|
| 1 | フォーカスを「コンパイル結果の詳細」へ移動 | `Tab` |
| 2 | 折りたたみ状態の読み上げを記録 | (自動読み上げ) |
| 3 | 押下して開く | `VO + Space` |
| 4 | 展開後の読み上げを記録 | (自動読み上げ) |

「折りたたみ済み」→「展開済み」と状態変化が読み上げられるかを見る。
ボタン名だけ読んで状態を言わない場合は差分として記録する。

### 4. フォームエラー: 入力検証

| # | 操作 | キー |
|---|---|---|
| 1 | フォーカスを入力欄へ移動 | `Tab` |
| 2 | ラベルの読み上げを記録 | (自動読み上げ) |
| 3 | `not-an-email` と入力 | (キーボード入力) |
| 4 | 「送信」へ移動して押下 | `Tab` → `VO + Space` |
| 5 | エラー発生時の読み上げを記録 | (自動読み上げ) |
| 6 | 入力欄へ戻る | `VO + ←` |
| 7 | エラーと紐付いた状態の読み上げを記録 | (自動読み上げ) |

見るべきは、入力欄にフォーカスを戻したときに
`aria-describedby` 経由でエラー文が読み上げられるか。
`role=alert` の即時読み上げとは別物なので両方記録する。

### 5. 条件付き描画: v-if と v-show

| # | 操作 | キー |
|---|---|---|
| 1 | フォーカスを「補足を切り替え」へ移動 | `Tab` |
| 2 | 押下して表示 | `VO + Space` |
| 3 | `VO + →` で後続要素を順に読ませ、2つの補足を記録 | `VO + →` |
| 4 | 再度押下して非表示 | `VO + Space` |
| 5 | `VO + →` で後続に補足が現れないことを確認 | `VO + →` |

`v-if` と `v-show` で読み上げの扱いが変わらないことを確認する。
非表示時にどちらか一方だけ読み上げられたら差分として記録する。

### 6. リスト描画: キー付き v-for の再利用

初期状態では1件目 (Vapor Mode) が選択済み。

| # | 操作 | キー |
|---|---|---|
| 1 | リストへ入り、3項目を順に読ませて記録 | `VO + →` |
| 2 | 3件目 (Hydration) へフォーカスを移動 | `Tab` ×3 |
| 3 | 押下して選択 | `Enter` |
| 4 | 選択直後の読み上げを記録 | (自動読み上げ) |
| 5 | 「先頭を末尾へ」へ移動して押下 | `Tab` → `VO + Space` |
| 6 | リストへ戻り、3項目を順に読ませて記録 | `VO + →` |
| 7 | 「先頭を削除」へ移動して押下 | `Tab` → `VO + Space` |
| 8 | リストへ戻り、2項目を順に読ませて記録 | `VO + →` |

**このカテゴリは ariaSnapshot では観測しきれない部分がある。** 見るべきは3点。

- **位置の読み上げ** — 「3項目中の1」のように位置が読まれるか。
  `aria-posinset` / `aria-setsize` は ariaSnapshot の出力に現れないため、
  E2E 側では属性値を別時点として保存している。読み上げに乗るかは別問題なので
  ここで確認する
- **並べ替え後に位置が更新されるか** — 手順6で選択中の Hydration が
  「3項目中の2」と読まれるか。古い位置のまま読まれたら差分として記録する
- **削除後に総数が更新されるか** — 手順8で「2項目中の1」と読まれるか

並べ替えでは DOM ノードが再利用される (E2E で確認済み)。**支援技術が
古い値をキャッシュしていると、DOM の属性は正しいのに読み上げだけ古くなる**
可能性があり、それはこの手順でしか見つからない。

### 7. コンポーネント合成: props / slots

入力欄のラベルは親、入力欄本体は子が持ち、両者は props で渡した id だけで
繋がっている。**ラベルが読まれれば境界越しの参照が生きている。**

| # | 操作 | キー |
|---|---|---|
| 1 | 入力欄へフォーカスを移動 | `Tab` |
| 2 | 読み上げを記録 (「表示名」と読まれるか) | (自動読み上げ) |
| 3 | 説明文まで読まれるか記録 (「全角32文字まで」) | (自動読み上げ) |

`aria-describedby` の読み上げは詳細度の設定に依存する。読まれない場合は
「詳細度の設定で読まれない」と書き、✕ にはしない (差分ではないため)。

### 8. Teleport: body 直下へ移すダイアログ

項目2 (フォーカス管理) と操作は同一で、違いはダイアログの描画位置だけ。
**2つを見比べるのが目的**なので、項目2と同じ詳細度で連続して行う。

| # | 操作 | キー |
|---|---|---|
| 1 | 「通知パネルを開く」へフォーカスを移動 | `Tab` |
| 2 | 押下してダイアログを開く | `VO + Space` |
| 3 | 開いた直後の読み上げを記録 | (自動読み上げ) |
| 4 | ダイアログの外へ出られるか試す | `VO + →` を繰り返す |
| 5 | 「閉じる」を押し、復帰先の読み上げを記録 | `VO + Space` |

**項目2との差が本題。** ダイアログは `body` 直下にあり `main` の外にいる。
DOM 上の位置が変わっても読み上げ順序や境界の扱いが同じか、
項目2の記録と並べて比較する。異なれば `aria-modal` が同じでも
体験が違うことになり、機械比較では出ない発見になる。

### 9. Transition: 退場アニメーション中のツリー

**E2E で「退場中は `role=alert` がツリーに残る」ことを確認済み**
(classic / vapor 共通)。ここで見たいのは、それが読み上げに乗るか。

| # | 操作 | キー |
|---|---|---|
| 1 | 「警告を出す」へフォーカスを移動して押下 | `Tab` → `VO + Space` |
| 2 | 警告の読み上げを記録 | (自動読み上げ) |
| 3 | 同じボタン (「警告を閉じる」) を押下 | `VO + Space` |
| 4 | 閉じた直後に警告が再度読まれないか記録 | (自動読み上げ) |

手順4で警告が読み上げられたら、それは**残留がユーザーに届いている**という
こと。差分ではない (両系統で起きる) が、Transition を使う設計上の注意点として
所見に書く。

### 10. 動的コンポーネント: :is による差し替え

| # | 操作 | キー |
|---|---|---|
| 1 | 「内訳へ切り替える」へフォーカスを移動して押下 | `Tab` → `VO + Space` |
| 2 | 差し替え後の領域を読ませて記録 (「内訳」) | `VO + →` |
| 3 | 「概要へ切り替える」を押下 | `VO + Space` |
| 4 | 戻した後の領域を読ませて記録 (「概要」) | `VO + →` |

手順4で「内訳」と読まれたら、古い名前が残っている。
E2E では属性値が正しく入れ替わることを確認済みなので、
そこで差が出れば**支援技術側のキャッシュ**が原因になる。

### 11. SSR / hydration

**この項目だけ URL が違う。** 他の10項目は `index.html` (クライアント描画) だが、
ここは `/ssr.html` を開く。

```
classic → http://localhost:4173/ssr.html
vapor   → http://localhost:4174/ssr.html
```

サーバが描いた HTML は両 lane でバイト単位で同一 (`scripts/prerender.mjs` が
毎回ハッシュを突き合わせる)。それを classic は `createSSRApp`、vapor は
`createVaporSSRApp` という**別実装**で引き継ぐ。したがってここで読み上げに
差が出れば、原因は hydration 実装の差以外にありえない。

| # | 操作 | キー |
|---|---|---|
| 1 | `/ssr.html` を開き、`main` を頭から3項目ぶん読ませて記録 | `VO + →` |
| 2 | 「補足を切り替え」へフォーカスを移動して押下 | `Tab` → `VO + Space` |
| 3 | 差し込まれた補足の読み上げを記録 | `VO + →` |
| 4 | 再度押下して閉じ、補足が読まれなくなることを記録 | `VO + Space` → `VO + →` |

**手順1が本題。** hydration はサーバが描いた既存の DOM を後から乗っ取るため、
支援技術が乗っ取り前のツリーを掴んだままだと、画面の内容と読み上げが食い違う。
`index.html` (項目1〜10) はクライアントが最初から描くのでこの経路を通らない。

手順2以降は hydration が実際に繋がったことの確認。サーバの HTML には
イベントが載っていないので、押して反応があればクライアント側が接続済みと判断できる。
無反応なら hydration そのものが失敗しており、手順1の記録も無効になる。

> E2E では hydration の前後でツリーが変化しないことを確認済み
> (`ssr-hydration.server.yaml` と `ssr-hydration.hydrated.yaml` が同一)。
> `v-model` 由来の hydration mismatch 警告が両 lane で等しく出るが、
> これは Vapor 起因ではない (README「SSR / hydration」)。

## 環境の明記が必須

読み上げ挙動は下記に強く依存するため、発表資料と README に必ず書く。

- macOS のバージョン
- Safari のバージョン
- VoiceOver の詳細度設定 (「詳細度」→ 「テキストの読み上げ」など)

環境が違えば結果は再現しない。「差分なし」という結論の適用範囲を
明示するために書く。
