vue-vapor-a11y-experiment / 手動検証

Vapor Mode のアクセシビリティ検証を手で回す

classic (VDOM) と vapor (Vapor Mode) の2系統を同一ソースから展開し、機械比較 (ariaSnapshot) と 人による読み上げ確認 (VoiceOver) の両方で差分を取るための作業手順。 上から順に実行すれば、リポジトリの検証結果を最初から再現できる。

Node.js
22.x 以上 (20.19+ 可)
パッケージ管理
pnpm 11.x（npm 不可）
検証対象
vue@3.6.0-rc.3
スクリーンリーダー
VoiceOver (macOS) + Safari
検証カテゴリ
5 カテゴリ / 15 スナップショット
PART A

リポジトリの手動検証

ステップ 01 から 07 は前のステップの成果物に依存するため、順番に実行する（08 は任意）。 各ステップの「期待される結果」と手元の出力が食い違ったら、その場で止めて 巻末の早見表か troubleshooting.md を見る。

01

依存関係をインストールする

vue@3.6.0-rc.3 は semver 上プレリリース扱いのため、npm では @vitejs/plugin-vue の peer dependency vue@^3.2.25 を満たさないと判定され ERESOLVE で失敗する。pnpm を使うこと。

コマンド 
node -v          # 22.x 以上であること
pnpm -v          # 11.x であること
pnpm install
期待される結果
エラーも peer dependency 警告も出ずに完了する。
02

2系統へ配布し、同一性と型を確認する

この検証の前提は「classic と vapor のコンポーネントソースはバイト単位で同一」という点にある。 Vapor モードの指定はビルド設定側にあり、コンポーネントには現れない。 ここが崩れると、観測された差分の原因を Vapor Mode に帰属できなくなる。 手で編集してよいのは source/components/ と e2e/scenarios/ だけで、 apps/*/src/ は pnpm run sync の生成物。

コマンド 
pnpm run sync
pnpm run typecheck

diff -r apps/classic/src/components apps/vapor/src/components
期待される結果
synced -> apps/classic/src (7 files) synced -> apps/vapor/src (7 files) ✅ 全 lane のソースがバイト単位で同一 (7 files) （typecheck も diff も何も出力しない）
型チェックは配布後を見ている

source/components/App.vue が参照する ./components/*.vue は 配布先のレイアウトを前提にしたパスで、source/ 配下では解決できない。 そのため tsconfig.json の対象は apps/*/src になっている。 pnpm run sync を通していないと古いコードを検査するので順序が重要。 検査対象を確認したいときは pnpm exec vue-tsc -p tsconfig.json --listFiles | grep apps/ で両 lane 分が出るかを見る（include が何も拾わなくても vue-tsc は成功で終わる）。

なぜ置換をやめたか

以前は vapor 側だけ <script setup> を <script setup vapor> に 文字列置換していた。完全一致に依存するため、たとえば lang="ts" を付けた途端に 無言で不一致になり、vapor 側が classic としてビルドされて「差分なし」という 偽の成功を出す危険があった。現在はビルド設定側の features.vapor で指定しており、 判定条件は <script setup> の有無のみで lang="ts" に依存しない。

03

両系統をビルドする

このあとのスモークテストと E2E はどちらもビルド成果物 (apps/*/dist) を読む。 ここでバンドルサイズも記録しておくと、ランタイム差の根拠になる。

コマンド 
pnpm run build   # build:classic と build:vapor をまとめて実行する
期待される結果（2026-08-22 計測時の参考値 / 6カテゴリ）
classic

71.48 kB / gzip 28.07 kB

vapor

59.29 kB / gzip 22.72 kB

vapor 側は VDOM ランタイムを含まないぶん gzip で約 19% 小さい。

この数字は機能セット依存

削減率は 1カテゴリ時点で約 37%、5カテゴリで 28.3%、 v-for を加えた6カテゴリで 19.1% と落ちている。 差の絶対値そのものが 7.77 kB → 5.35 kB に縮んでいる点が重要で、 アプリコードが両系統に等しく積み上がるだけなら比率は縮んでも絶対値は変わらない。 つまり vapor 側だけが余分に太った。v-for 1つの増分は gzip で classic +0.63 kB に対し vapor +3.05 kB。 Vapor は createFor / ForBlock を新たに引き込み、 それが内部で watch を使うため reactivity 側 （watch / traverse / shallowRef）まで入る。 classic は VDOM の汎用パッチ機構が最初から入っているので増分が小さい。 発表で「Vapor は N% 小さい」と言うときは計測時点の機能セットを併記する。

04

ガードを検証する（この検証の要）

「Vapor モードが効いていないまま両系統を classic としてビルドしていた」という 事故を防ぐための検証。この状態でも E2E は通り差分ゼロが出てしまうため、 ここを通していない「差分なし」は結果として扱えない。 差分レポートを読む前に必ず実行する。

コマンド 
pnpm run verify
期待される結果
✅ 全 lane のソースがバイト単位で同一 (7 files) | lane | 期待 vapor | 期待マウント関数 | HTML文字列テンプレート | VNode props | 判定 | |---|---|---|---|---|---| | classic | false | createApp | 0 | 16 | ✅ OK | | vapor | true | createVaporApp | 9 | 0 | ✅ OK | ✅ 両 lane が意図どおり別のコンパイル戦略でビルドされています
何を見ているか
検証内容防ぐ事故
2系統のコンポーネントソースがバイト単位で同一片方だけ編集し、差分の原因を Vapor だと取り違える
ビルド設定と entry が lane のあるべき姿と一致設定を間違えたまま比較して気付かない
成果物が意図したコンパイル戦略で生成されているプラグインが指定を無視し、classic 同士を比較する
判定

どちらかの lane が ❌ NG なら、そこで止める。出力されたメッセージ別の対処は troubleshooting.md の 「pnpm run verify が失敗する」を見る。 この状態で得た「差分 0 件」は無効。

05

スモークテストで配線を確認する

happy-dom 上でビルド成果物を読み込み、「保存」ボタンの押下が role=status に 反映されるかだけを見る最小チェック。Vapor は素の DOM API を直接叩くため、 ここで落ちるならアクセシビリティ以前の問題。

コマンド 
pnpm run smoke
期待される結果
[classic] click前: "" → click後: "保存しました" [vapor] click前: "" → click後: "保存しました"
つまずきやすい点

dist が見つからない場合はステップ 03 を先に実行する。ステップ 08 の --minify false ビルドを行った直後も、通常ビルドに戻してから実行すること。

06

ariaSnapshot を取得する（E2E）

Playwright が classic を :4173、vapor を :4174 でプレビュー起動し （ビルドも自動で走る）、6カテゴリ × 各時点のアクセシビリティツリーを e2e/snapshots/{classic,vapor}/ に YAML で保存する。 ブラウザ本体が未取得の場合は初回だけインストールが要る。

preview を立てたままでは失敗する

Part B の pnpm run preview:{lane} を起動したまま実行すると Error: http://localhost:4173 is already used で落ちる。 これは意図的。既存サーバを再利用すると、それが古い成果物を 配信していても Playwright は気付かず「差分 0 件」を出してしまう。 preview を止めてから実行する。

コマンド 
pnpm exec playwright install chromium   # 初回のみ
pnpm run test:e2e
期待される結果
全シナリオ pass。e2e/snapshots/classic と e2e/snapshots/vapor に それぞれ 29 個の .yaml が生成される。
タイミング由来の偽陽性に注意

スナップショット取得前に状態が確定していないと、Vapor とは無関係な差分が出る。 シナリオを足すときは必ず expect(...) で状態を待ってから取得する。

07

差分レポートを生成して読む

比較の向きは「classic の同一時点 vs vapor の同一時点」。 同じ系統内の before / after を比べているのではない。

コマンド 
pnpm run diff
open results/diff-report.md
期待される結果
results/diff-report.md を出力 (29件中 差分あり 0件)
差分が「あり」になった場合の切り分け
症状まず疑うこと
特定シナリオだけ差分ありスナップショット取得前の待ち合わせ不足。expect を足して再実行する
全シナリオで差分ありステップ 04 の pnpm run verify を通しているか確認する
vapor 側だけ「取得なし」:4174 のプレビューが立っていない、または vapor 側のシナリオが失敗している
08

（任意）生成コードそのものを読む

コンパイル方式が切り替わっているかの判定はステップ 04 の pnpm run verify で 済んでいる。このステップは発表資料向けに「Vapor が実際にどんなコードを吐くか」を 目で確かめたいときだけ行う。minify なしでビルドして成果物を grep する。

コマンド 
pnpm exec vite build --config apps/vapor/vite.config.mjs --minify false
pnpm exec vite build --config apps/classic/vite.config.mjs --minify false

grep -oE 'template\("[^"]{0,40}|setText|setAttr|VaporComponent|createIf' \
  apps/vapor/dist/assets/*.js | sort -u
grep -oE 'createElementBlock|createVNode|openBlock|toDisplayString' \
  apps/classic/dist/assets/*.js | sort -u
期待される結果
vapor 側に出る

VaporComponent / createIf / setAttr / setText / template("<div role=dialog aria-modal=true …

HTML 文字列テンプレート + 直接 DOM 操作。静的な aria 属性が template() の文字列に焼き込まれている点が重要。

classic 側に出る

createElementBlock / createVNode / openBlock / toDisplayString

VNode 生成を経由する従来のコンパイル戦略。

後始末（必須）

観察後は pnpm run build で通常ビルドに戻す。minify なしの成果物は サイズが大きく、そのままだとバンドルサイズの計測値として使えないうえ、 スモークテストや E2E にも影響する。

PART B

macOS VoiceOver での読み上げ検証

ariaSnapshot はアクセシビリティツリーの構造を機械的に比較できるが、 「スクリーンリーダーが実際にどう読み上げるか」までは保証しない。そこを埋めるのがこの検証。 記録先は results/voiceover-log.md。

唯一かつ最重要のルール

classic (localhost:4173) と vapor (localhost:4174) で 完全に同じキー操作を行う。操作が違えば、読み上げの違いが Vapor 起因なのか操作起因なのか切り分けられなくなる。

カテゴリを移動するたびにページを再読み込みする。前の操作で残った状態 （開いたままのダイアログ、表示済みのエラー）が次の読み上げに混ざると、差分の原因を追えなくなる。

準備 1 — ビルドとガード検証を先に通す

Vapor モードが効いていない状態で読み上げを比べても、classic 同士を聞き比べているだけになる。 ariaSnapshot と違って読み上げ検証は手作業なので、後から気付いても全カテゴリやり直しになる。 

pnpm run sync && pnpm run typecheck && pnpm run build && pnpm run verify

準備 2 — プレビューサーバを2つ起動する

別々のターミナルで起動し、検証中は両方立てたままにする。

pnpm run preview:classic   # → localhost:4173
pnpm run preview:vapor     # → localhost:4174
ビルドを含めていない理由

準備1で verify を通した成果物をそのまま配信するため。ここで再ビルドすると、 検証した成果物と配信する成果物が別物になりうる。

ポートは scripts/lanes.mjs の previewPort が単一の情報源で、 strictPort: true が付いている。埋まっていれば Error: Port 4173 is already in use で失敗し、別ポートへ逃げない。 逃げてしまうと 4174 が埋まっていて vapor が 4175 で起動し、4173 に残った classic を相手に 「classic 同士」を比較する事故が起きる。VoiceOver は何も言わずに読み上げるので、 この事故は自力では気付けない。

操作中の lane はタブのタイトル（classic / vapor）で確認する。 index.html の <title> を lane ごとに変えているのはこのため。

準備 3 — VoiceOver とキャプションパネル

読み上げ内容を画面に字幕表示させる。録画にそのまま残るので、あとから文言を突き合わせられる。 以下の VO は Control + Option の同時押しを指す。

#操作キー
1VoiceOver を起動する⌘ + F5
2VoiceOver ユーティリティを開くVO + F8
3「ビジュアル」→「キャプションパネル」を有効化する—
4画面収録を開始する（マイク ON で読み上げ音声も残る）⇧ + ⌘ + 5

記録の取り方

  • 読み上げ全文はキャプションパネルの表示テキストをそのまま書き写す。聞き取りでの書き起こしは表記ゆれが入るため不可。
  • 一致欄は ◯ / ✕ のみ。「ほぼ同じ」は ✕ として、違いの内容を本文に書く。
  • ✕ が出たら、まず該当カテゴリの ariaSnapshot に差分が出ていないかを確認する。 ツリーは一致しているのに読み上げだけ違うなら、それはこの検証でしか見つからない最も価値のある発見。

以下の6カテゴリを、それぞれ classic → vapor の順で同一操作する。

B1

live region: トースト通知

#操作キー
1Safari で対象 URL を開く—
2フォーカスを「保存」へ移動し、読み上げを記録するTab
3ボタンを押下するVO + Space
4live region の読み上げを記録する（自動読み上げ）

見るべき点：role=status は控えめな通知なので、読み上げ中の内容を中断しない。 中断されるようなら差分として記録する。

B2

フォーカス管理: モーダルダイアログ

#操作キー
1フォーカスを「設定を開く」へ移動するTab
2押下してダイアログを開き、直後の読み上げを記録するVO + Space
3フォーカスを「閉じる」へ移動するTab
4押下して閉じ、直後の読み上げを記録するVO + Space
5ダイアログの外へ出られるか試すVO + →

最も差分の出る可能性が高い項目。見るべきは3点。

  • 開いたとき「ダイアログ 表示設定」のようにロールごと読み上げるか
  • 閉じたときフォーカスが「設定を開く」に戻り、それが読み上げられるか
  • ダイアログの外に VO + → で出られてしまわないか（aria-modal の効き）
B3

動的 aria 属性: 開閉パネル

#操作キー
1フォーカスを「コンパイル結果の詳細」へ移動するTab
2折りたたみ状態の読み上げを記録する（自動読み上げ）
3押下して開き、展開後の読み上げを記録するVO + Space

見るべき点：「折りたたみ済み」→「展開済み」と aria-expanded の状態変化が 読み上げられるか。ボタン名だけ読んで状態を言わない場合は差分として記録する。

B4

フォームエラー: 入力検証

#操作キー
1フォーカスを入力欄へ移動し、ラベルの読み上げを記録するTab
2not-an-email と入力する（キーボード入力）
3「送信」へ移動して押下し、エラー発生時の読み上げを記録するTab → VO + Space
4入力欄へ戻り、エラーと紐付いた状態の読み上げを記録するVO + ←

見るべき点：入力欄にフォーカスを戻したとき aria-describedby 経由で エラー文が読み上げられるか。role=alert の即時読み上げとは別物なので、両方を別々に記録する。

B5

条件付き描画: v-if と v-show

#操作キー
1フォーカスを「補足を切り替え」へ移動するTab
2押下して表示するVO + Space
3後続要素を順に読ませ、2つの補足を記録するVO + →
4再度押下して非表示にするVO + Space
5後続に補足が現れないことを確認するVO + →

見るべき点：v-if（DOM ごと出入り）と v-show（display 切り替え）で 読み上げの扱いが変わらないこと。非表示時にどちらか一方だけ読み上げられたら差分として記録する。

B6

リスト描画: キー付き v-for の再利用

初期状態では1件目（Vapor Mode）が選択済み。

#操作キー
1リストへ入り、3項目を順に読ませて記録するVO + →
23件目（Hydration）へフォーカスを移動するTab ×3
3押下して選択するEnter
4選択直後の読み上げを記録する（自動読み上げ）
5「先頭を末尾へ」へ移動して押下するTab → VO + Space
6リストへ戻り、3項目を順に読ませて記録するVO + →
7「先頭を削除」へ移動して押下するTab → VO + Space
8リストへ戻り、2項目を順に読ませて記録するVO + →

見るべき点は3つ。

  • 位置が読まれるか — 「3項目中の1」のように読まれるか。 aria-posinset / aria-setsize は ariaSnapshot の出力に現れないため、 E2E 側では属性値を別時点として保存している。読み上げに乗るかは別問題なのでここで確認する。
  • 並べ替え後に位置が更新されるか — 手順6で選択中の Hydration が 「3項目中の2」と読まれるか。古い位置のまま読まれたら差分として記録する。
  • 削除後に総数が更新されるか — 手順8で「2項目中の1」と読まれるか。
このカテゴリでしか見つからないもの

並べ替えでは DOM ノードが再利用される（E2E で data-probe により確認済み）。 支援技術が古い値をキャッシュしていると、DOM の属性は正しいのに読み上げだけ古くなる 可能性があり、それは機械比較では検出できない。

環境の明記は必須

読み上げ挙動は以下に強く依存し、環境が違えば結果は再現しない。 「差分なし」という結論の適用範囲を示すために、発表資料と README に必ず書く。

pnpm run preview:{lane} が Port is already in use で落ちる そのポートに何かが立っている（strictPort: true で別ポートへ逃げない） lsof -nP -iTCP:4173 -sTCP:LISTEN で特定して止める（vite は [::1] にバインドする）
取得タイミング由来の差分が出る スナップショット取得前に状態が確定していない expect(...) で待つ。それでもブレるなら page.waitForLoadState() を足す
